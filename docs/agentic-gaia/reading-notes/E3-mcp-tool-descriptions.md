## What the paper is
(1) A rubric for MCP tool descriptions with six components: Purpose, Guidelines (when/how to use), Limitations, Parameter Explanation, Length & Completeness, Examples. Built from Anthropic's MCP docs plus 15 community sources found with OpenAI Deep Research (4 tutorials, 4 blog posts, 3 Reddit threads, 3 research articles, 1 GitHub discussion); two authors' open coding agreement Jaccard 0.92 (Sec. 4.1, pp. 10-13). Each component is scored 1-5; a mean below 3 is a "smell" (Unclear Purpose, Missing Usage Guidelines, Unstated Limitations, Opaque Parameters, Underspecified or Incomplete, Exemplar Issues) (Sec. 4.1.4, Fig. 6, pp. 13-14).
(2) A scan of 856 tools in 103 MCP servers (23 official, 80 community; taken from four earlier MCP benchmark papers, as of 20 Aug 2025; descriptions extracted via `tools/list`) with an LLM-as-jury of gpt-4.1-mini, claude-haiku-3.5 and qwen3-30b-a3b (Sec. 4.2-4.3, pp. 14-16).
(3) An FM "augmentor" (GPT-4.1-mini) that rewrites descriptions to fill all five content components; Examples and Limitations are grounded on execution traces produced by running generated tasks against the real server (Sec. 4.4, pp. 17-18); a "Tool Description Router" in the MCP client that swaps description variants at runtime (Sec. 4.5.2, p. 19).
(4) A benchmark evaluation on MCP-Universe (231 tasks, six domains, 202 tools on 18 servers; execution-based evaluators) with four models, plus a component ablation (Sec. 4.5, 5.2-5.3).

## Key results (with locators)
1. **Prevalence (RQ1, Fig. 7, Table 4, pp. 22-23).** At least one smell in 97.1% of the 856 descriptions. By type: Unstated Limitations 89.8%, Missing Usage Guidelines 89.3%, Opaque Parameters 84.3%, Underspecified or Incomplete 79.1%, Exemplar Issues 77.9%, Unclear Purpose 56.0%. Smell-free rate: Purpose alone 44.0% (376 tools); Purpose + Guidelines 10.4%; + Limitations 7.5%; + Parameter Explanation 3.0%; all five 2.9% (25 tools). Official vs community servers do not differ significantly on any component (Mann-Whitney U, Bonferroni; all adjusted p = 1.0; Table 5, p. 23). Example of a smelly description: "Creates PayPal Invoice Link." (Fig. 9, p. 24).
2. **Rubric scorer validity (Tables 1-2, pp. 16-17).** Jury agreement ICC(2,1): Purpose 0.82, Guidelines 0.85, Limitations 0.84, Parameter Explanation 0.90, Length 0.76, Examples 0.62. Weighted Cohen's kappa jury vs two human authors on 90 random tools: 0.72-0.89. The scorer is an LLM; "smell" is a rubric-defined label, not an observed failure (Sec. 6.3).
3. **Augmentation raises rubric scores (Table 6, p. 25; recomputed as Table 13, p. 35).** Median component scores rise from 1.0-2.0 (Table 6: Purpose 2.0, Length 1.3, others 1.0) to 4.7-5.0 (Wilcoxon p < 0.001 for every component). The authors replaced Table 6 by Table 13 after re-scoring the "before" descriptions with source-code grounding (Parameter Explanation before-median 1.0 -> 2.0; Sec. 6.1). The jury is scoring text that another LLM wrote to the same rubric, so this is a check that the augmentor follows the rubric, not independent evidence of quality.
4. **Task success, MCP-Universe (RQ2, Table 7, p. 26).** 4 models x 6 domains = 24 cells (one "Could not run": GLM-4.5 Repo Management). Improved in 54.17% of cells, regressed in 16.67% (4 cells), unchanged or failed 29.16%. Largest gains: Qwen3-Coder-480B Finance +32.5 pp (40.0 -> 72.5%), GPT-4.1 Location Navigation +22.1, GPT-4.1 Finance +17.5, GLM-4.5 Finance +17.5. Regressions: GLM-4.5 Web Searching -9.1, Qwen3-Coder 3D Design -5.2, Browser Automation -2.6, Web Searching -1.8. Reported "Cross-Model Median dSR" 5.85 pp.
5. **Overall per-model change (Table 8, p. 27).** SR: GPT-4.1 18.18 -> 29.44; Qwen3-Coder 19.91 -> 25.97; GLM-4.5 24.68 -> 25.25; Qwen3-Next-80B 15.58 -> 21.21. Average evaluator score AE: 0.41 -> 0.47, 0.38 -> 0.43, 0.41 -> 0.45, 0.33 -> 0.39 (median change +15.12%). Average steps AS: 5.24 -> 8.08, 7.78 -> 14.06, 7.33 -> 14.79, **9.46 -> 6.97 (a decrease for Qwen3-Next)**; median change +67.46%. McNemar test on SR: p = 0.02 (p. 26); AE: Wilcoxon p < 0.01; AS significantly higher for three models (p < 0.001, p. 27). Absolute success rates stay low (15-29%).
6. **Reader's check of the headline medians (calculation from the printed tables, not stated by the authors).** The "5.85" equals the median of the four model-level SR changes in Table 8 (+11.26, +6.06, +0.57, +5.63 pp), and the "67.46%" equals the median of the four model-level relative AS changes (+54.2%, +80.7%, +101.8%, -26.3%). The median of the 23 valid per-cell dSR values in Table 7 is **+2.57 pp** (13 improved, 6 unchanged, 4 regressed). Table 7's footer labels 5.85 "Cross-Model Median dSR".
7. **Cost (Table 9, p. 28; Fig. 10, p. 29).** Qwen3-Next-80B, three domains: median input tokens +21.85% to +41.43%, output tokens +11.10% to +69.00% (Finance 50.64K -> 61.71K input; Repo Management 232.41K -> 299.86K; 3D Design 43.19K -> 61.09K). 68-78% of tasks needed more steps; of those, 41-55% improved AE, but only 19-20% of all tasks improved in final success. Pareto: Qwen3-Next-80B-A3B often on or near the frontier; GPT-4.1 close to ideal; larger open models (GLM-4.5, Qwen3-Coder-480B) mostly dominated (Fig. 11, p. 30).
8. **Component ablation (RQ3, Tables 10-11, Fig. 12, pp. 30-34).** Five (model, domain) cells (Finance/GPT-4.1; Location Navigation/GPT-4.1; Repo/Qwen3-Coder; 3D Design/Qwen3-Coder; Web Search/GLM-4.5), 25 runs. "No single golden combination": Finance/GPT-4.1 best with Purpose + Guidelines only (67.5% vs fully augmented 57.5%); Location Navigation best with all components (31.0%); Repo best with Purpose+Guidelines+Limitations+Parameter Explanation (21.21% vs 18.2%); 3D Design best with Purpose + Examples (26.32% vs 21.1%); Web Search tie (18.18%). Dropping Examples (P+G+L+PEx) gives median SR 21.21% vs 21.10% for full; Cochran's Q p > 0.20 across FR / best combination / P+G+L+PEx: Examples removal "does not significantly degrade performance". The best reduced combination and the full description solve overlapping but different tasks (confusion matrix 46 both / 15 / 11 / 120 failed both); combining them would reach 37.8% on Location Navigation (hypothetical). An example of harm: a vague, self-referential Limitation sentence generated for `get_historical_stock_prices` "dilutes otherwise useful guidance" (p. 31).
9. **Source-code grounding (Sec. 6.1-6.2, Tables 12-14, pp. 34-37).** Source code found for 183 of the 202 MCP-Universe tools (OpenAPI for 17). Grounding raises the scorer's Parameter Explanation rating (median 1 -> 2, r = 0.60) and improves faithfulness of augmented text (rank-biserial 0.66-0.86 for Purpose, Guidelines, Limitations, Parameter Explanation). But on 92 re-executed tasks (Finance, Repo, 3D) the grounded descriptions solved 26 and the ungrounded 35 (McNemar exact p = 0.064; 5 tasks were solved only with grounding). Authors: "a reliability-oriented safeguard rather than a guaranteed performance optimization".
10. **Implications proposed (Sec. 7, pp. 37-40).** CI smell scanning, prioritise a few high-leverage components, structured per-component fields in the MCP spec so clients can load Purpose first and lazily add Guidelines/Examples, client-side overrides of descriptions, resource caps (max steps/tokens) when enabling richer descriptions, registry quality badges.
11. **Threats (Sec. 8, pp. 40-43).** MCP-Universe covers 202 of the 856 tools; baselines for three models are aggregated numbers from the earlier MCP-Universe paper and not re-run; Qwen3-Next-80B was run with a partial augmentation (Purpose, Guidelines, Limitations only; no Parameter Explanation or Examples; Browser Automation examples excluded for all models); the Web Searching tasks used a different Google-search MCP server from the baseline study; agent runs are non-deterministic; the ablation cells were selected from cells known to be sensitive (selection bias).

## Corrections to the current literature-review.md entry (E3)
Entry: "ACM TOSEM (doi 10.1145/3858625; arXiv:2602.14878) ... 97.1% of 856 tools across 103 servers have at least one description smell. Augmenting descriptions raised task success by a median of 5.85 pp. It also increased execution steps by 67.46%, and performance fell in 16.67% of cases." Route: Scite + WebFetch. Depth: abstract (WF).
- **Venue:** the arXiv page and the v3 PDF do not name TOSEM and carry a placeholder DOI; the TOSEM DOI is confirmed only by Crossref (published online 2026-10-15). Cite as "arXiv v3 (31 May 2026); VoR in TOSEM, DOI 10.1145/3858625, not read". The numbers quoted match arXiv v3 (they match the abstract that Crossref also holds).
- **"median of 5.85 pp" needs scoping.** It is reported as the median change across models in Table 8 (median of four per-model SR deltas, 0.57 to 11.26 pp); the median over the 23 per-domain-model cells in Table 7 is 2.57 pp (my calculation). Three of the four models' "original" numbers are aggregate baselines taken from the earlier MCP-Universe paper (different run, not paired, Web Search server swapped); only Qwen3-Next-80B has paired baseline and augmented runs, and for it the augmentation was partial. The significance test (McNemar p = 0.02) is therefore on one model's paired data. Absolute success rates are 15-29% overall.
- **"increased execution steps by 67.46%":** median across four models of relative changes (+54%, +81%, +102%, and **-26% for Qwen3-Next**); not a per-task statistic. Token growth was measured only for Qwen3-Next in three domains (input +22% to +41%, output +11% to +69%).
- **"performance fell in 16.67% of cases":** 4 of 24 domain-model cells (not 16.67% of tasks); another 29.16% of cells were unchanged or not run.
- **Missing for the design question:** (a) no single best component set; (b) Examples can be dropped without a significant loss; (c) compact variants (Purpose + Guidelines) sometimes beat the full text; (d) smell scores are LLM-jury rubric labels, "potential indicators of risk"; (e) grounding descriptions in source code improved faithfulness but not task success (26 vs 35 solved, p = 0.064); (f) official and community servers are equally smelly; (g) the benefit may be smaller for tools wrapping widely known services (Yahoo Finance, GitHub, Blender), which the authors suggest are "probably present extensively in FM training data".

## Design relevance
- **Write each Gaia tool description around Purpose + Guidelines (when to use it / when not to) and an explicit Limitations line (what persists across calls, what a snapshot restores, what time advance does), keep parameter prose short because the MCP input schema already carries names and types, and leave Examples out unless a tool is unfamiliar.** This follows RQ3: compact Purpose + Guidelines often equalled or beat the full text, and Examples removal was not significant.
- **Nu/Gaia is outside the training distribution:** the authors suspect that descriptions matter less for tools wrapping famous APIs, so richer descriptions (and examples drawn from real runs) may matter more for `gaia_eval`, `gaia_symbol`, snapshot and time tools. This is an inference, not tested here.
- **Derive Limitations and Examples from real tool traces, not by free generation:** the paper generates tasks, runs them against the server and distils limitations from outcomes (including error cases and "isError=false even on error" surprises). A recorded trace of Gaia tool calls (successes and failures) is the right source for these sections.
- **Budget the cost of the description text:** richer descriptions raised input tokens 22-41% on a small model and steps by +54% to +102% for three of four models; set a step cap and measure both success and steps when changing a description. Use a client-side description override (the Router idea) to A/B variants without rebuilding the server.
- **Treat the description as a testable artifact:** run a rubric scan (CI-style) on each tool description and re-run a fixed task set after each change; do not rely on rubric scores alone, since a better-scored description regressed in 4 of 24 cells.

## Limits / credibility
- Venue: ACM TOSEM (journal) per Crossref, so peer-reviewed; the version read is the preprint v3, not the VoR. Credibility-gate label suggestion: `eligible_for_claim_subject_to_article_appraisal` for "descriptions in the wild are mostly incomplete" (RQ1, scorer-dependent) and `context_or_prior_art_only` for the effect sizes in RQ2-RQ3 (small, mostly unpaired benchmark comparison).
- LLM-as-judge for smells (three small/older models) with human validation on 90 tools; augmentation also LLM-generated (GPT-4.1-mini, Claude Sonnet 4.5 for trace grounding), so a successful "improvement" confounds clarity with added information.
- MCP-Universe tasks are largely well-known public services; the original-baseline comparison is unpaired for three models; one run per cell; no confidence intervals on the SR changes in Table 7.
- Authors used LLMs for copy-editing and table layout (Disclaimer, p. 43); no conflict-of-interest statement in the text I read.
