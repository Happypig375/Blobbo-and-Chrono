## What the paper is
An agent runtime ("Planarian") that gives a coding/sysadmin/database/game agent three state-management primitives over a "statepoint": a consistent, restorable point-in-time version of the agent's environment (local files and running processes inside a sandbox, plus remote service state changed through MCP calls), carried together with "state evidence" (a description of the state and the outcomes of executions that previously proceeded from it) (Sec. 3, pp. 4-5, Fig. 2, Fig. 5).
- **Primitives (Table 2, p. 6):** `snapshot(sb, capture) -> sp`; `rollback(sp, sb, compensate)`; `fork(sp-local, sb) -> sb'`; hooks `capture` and `compensate` for remote services. The caller (user, harness or the agent itself, exposed as tools) chooses when to snapshot; the abstraction "does not require a snapshot after every call".
- **Context handling (Sec. 4.5, Table 3, pp. 6-7):** the agent's LLM context is not rewound; a context library records state descriptions and outcomes, exposes a "state ledger" for choosing a statepoint, and after rollback supplies a restore note that the harness appends. Without it "the agent might make decisions based on outdated or inconsistent context".
- **Local state (Sec. 5, pp. 7-8):** Podman sandbox; CRIU process checkpoints plus ZFS zero-copy snapshots; Algorithm 1 keeps CRIU checkpoints incremental across restores (clears soft-dirty bits in a pre-resume hook and fixes the parent-checkpoint timestamp) without changing CRIU or the kernel.
- **Remote state (Sec. 6, pp. 8-9):** a proxy MCP server rewrites supported calls into a compensable form and logs compensating actions, applied in reverse order on rollback. Prototype covers **SQL via a database MCP server**: pre-image statement, the original statement, post-image statement in one transaction. "Requests that cannot be made compensable are rejected before execution." Remote fork needs service-side branching (Neon, Dolt); compensation-only services cannot be forked.
- **Consistency (Sec. 6.2-6.3):** cgroup freeze of the container during snapshot, an exclusive lock while snapshot/rollback run, shared locks for tool calls; snapshots are taken between tool calls and can overlap LLM inference. Consistency across sandbox and external service assumes the service state is logically isolated per tenant.

## Key results (with locators)
1. **Agentic exploration in games (Sec. 7.2, Figs 6-7, p. 10).** GameWorld harness (three games; difficulty level picked per game where the agent makes the most progress within the step limit), 100 steps. Mean score by condition (No-snapshot / Planarian without rollback / Planarian): **Mario 23 / 93 / 357** (about 15x), **Flappy Bird 1.6 / 2.0 / 2.3 pipes** (1.4x), **Minecraft (simplified item-collection simulator with creepers and lava added by the authors) 9.1 / 12.3 / 12.5 dirt collected** (1.4x). The agent rolls back from a terminal state to an earlier statepoint, sees a ledger and restore context (with player-unobservable state filtered out), and tries an alternative. Fig. 6 error bars are large and (as read from the rendered figure) overlap between conditions in all three games; the number of runs and the meaning of the error bars are not stated in the text (searched for "runs", "trials", "seeds", "error bar"). The "no rollback" control (snapshot after every step, no rollback primitive) already reaches 12.3 of 12.5 on Minecraft and 93 of 357 on Mario; the authors note "snapshots may affect the timing of frames and may change the outcomes".
2. **Harness-driven tree search (Sec. 7.2, Fig. 8, p. 11).** MCTS-style search (SWE-search extended to arbitrary terminal tasks) on nine Terminal-Bench sysadmin tasks, GPT-5.6-luna (medium reasoning) traces replayed with recorded LLM latency: snapshot time 10x lower than Full-snapshot (about 94 s vs 909 s total), fork 2x lower (about 299 s vs 641 s), end-to-end 9% faster (about 5,786 s vs 6,314 s); the end-to-end gap is smaller because LLM latency hides snapshot cost.
3. **User-driven rollback overhead (Sec. 7.3, Figs 9-10, pp. 11-12).** Replayed traces, snapshot after each tool call, rollback at the end. Terminal-Bench (nine sysadmin tasks): No-snapshot end-to-end 1,893 s, Planarian 1,917 s (+1%), Full-snapshot 2,263 s (+20%); raw snapshot/rollback time 70 s vs 644 s (-89%). DevOps-Gym (16 implementation tasks): 3,096 s / 3,184 s (+2.8%, "less than 3%") / 4,924 s (+59%); Full-snapshot snapshot/rollback about 24x Planarian's.
4. **Local + remote consistency overhead (Sec. 7.4, Fig. 11, p. 12).** 50 Bird-interact-lite database tasks (PostgreSQL via MCP), traces replayed: end-to-end +3%; the proxy's rewrite makes MCP calls 1.3x slower per round trip, but "this request amplification only increases end-to-end time by less than 0.3%" (database calls are short next to LLM time).
5. **Microbenchmarks (Sec. 7.5, Figs 12-14, p. 12).** 8 GB working set: incremental snapshot 74x (memory workload) and 231x (file workload) faster than Full-snapshot; 11x faster than CRIU's native incremental for the first snapshot after a rollback; rollback 4x (memory) and 67x (file); fork 4x and 61x.
6. **Comparison table (Table 1, p. 4):** LangChain, OpenClaw, Podman, E2B, CubeSandbox, DeltaBox (sandbox checkpointing), SagaLLM, LogAct, Cordon (workflow recovery) each cover only part of: local state, remote state, local/remote consistency, context/environment consistency, snapshot/rollback/fork, and who can invoke (user, harness, agent). Planarian is marked as covering all.
7. **Workloads (Sec. 7.1, p. 10):** DevOps-Gym (704 tasks), Terminal-Bench 2.0 (89), Bird-interact-lite (300), GameWorld (34 games); agents mini-swe-agent, nanobot, SWE-search, GameWorld harness; Ubuntu 22.04 Xeon Silver 4310 (24 cores), 128 GB RAM, NVMe. Overhead experiments use a subset (9 tasks, 16 tasks, 50 tasks). No quality outcome (task success) is reported for the coding/DevOps/DB workloads; those sections only measure time overhead.

## Corrections to the current literature-review.md entry (F1)
Entry: "statepoints (snapshot, rollback, fork) across local and remote state. Authors report up to 15x task quality gains and 3% overhead for recovery." Route: Scite + WebFetch. Depth: abstract (WF). Preprint. Informs: "undo/branching for agent edits."
- **"up to 15x task quality" is one game.** It is Mario's mean score (23 -> 357 over 100 steps, error bars overlapping). The other two games gain 1.4x. Part of the gain is not the rollback primitive: the no-rollback control reaches 93 on Mario and 12.3 of 12.5 on Minecraft, and the authors acknowledge that snapshots change frame timing. "Task quality" here means in-game score or counts, not a quality judgement.
- **"3% overhead for recovery" is the worst of three replay measurements:** +1% (Terminal-Bench), +2.8% (DevOps-Gym), +3% (database tasks with local and remote state). These are measured on replayed traces with recorded LLM latency (the agent is not re-run), at a snapshot after each tool call, against baselines with +20% and +59% (Full-snapshot). Overhead depends on LLM latency hiding snapshot time; with faster inference "the end-to-end gap grows toward the performance gap" (p. 11).
- **Remote-state coverage is a prototype:** compensation exists only for SQL on one database MCP server; non-compensable requests are rejected; remote fork needs service-side branching. The claim "across local and remote state" holds only inside those limits.
- **Missing:** requires Linux sandbox stack (Podman + CRIU + ZFS) and all local tool execution inside the sandbox; the agent's context is not rewound but receives an appended restore note with prior-attempt outcomes ("state evidence"); no task-success results for coding, DevOps or database workloads, only overhead.
- **Missing:** the paper separates state (snapshotted) from evidence (kept across rollback), so a rolled-back agent still sees what already failed.

## Design relevance
- **Expose snapshot/rollback to the agent as ordinary tools and keep a per-snapshot ledger** with a one-line description and the outcome of each attempt that followed from it; after a rollback, return that ledger entry in the tool result so the agent knows what failed. This is the paper's "state evidence" plus "restore context", and it avoids rewinding the agent's conversation.
- **Cover every mutable surface in the snapshot or say explicitly that it is not covered.** The paper's consistency argument (local report vs database) applies to Gaia: the in-memory world, project/script files the agent edits on disk, and any saved scene must be restored together, otherwise rollback leaves files that disagree with the world. A rollback that restores only the world is the "restoring local state only" case the authors describe as inconsistent.
- **Snapshots taken between tool calls, with an exclusive lock** while a snapshot runs, is a simple rule that avoids torn state; Gaia's world snapshot is in-process and does not need CRIU, but the same "no snapshot during a running eval/tick" rule applies.
- **Hide snapshot latency under model latency** (snapshot asynchronously while the model is generating); here the per-call overhead became negligible only because LLM calls take seconds. For a live editor with an interactive-rate loop, measure snapshot cost against eval latency before snapshotting after every call.
- **Expect modest, game-dependent benefit from rollback-driven retries:** large only where deaths/resets make earlier states valuable (Mario); 1.4x elsewhere, and partly explained by controls. Evidence that rollback improves design quality in an editor does not exist in this paper.
- **Fork for parallel exploration needs isolated remote/state copies;** for Gaia this means forking the world snapshot into independent copies if the agent is to compare alternative designs.

## Limits / credibility
- Preprint v1, systems paper, no peer review stated; credibility-gate label: `context_or_prior_art_only`. Coauthor at Microsoft Security Response Center; no conflict statement found.
- Quality evidence is the GameWorld experiment alone (three games, 100 steps, run count and error bar meaning unstated). Other results are overhead measurements on replayed traces from a single model's trace generation (GPT-5.6-luna), on task subsets (9, 16, 50).
- Rollback is evaluated with the agent as caller only in the games; user-driven recovery is evaluated as time overhead, not as correctness of recovery outcomes.
- Prototype scope: Linux, containers, SQL-only compensation.
