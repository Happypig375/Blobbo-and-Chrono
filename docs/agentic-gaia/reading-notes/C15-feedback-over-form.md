## What the paper is
A small-model study with two parts: (a) a manual comparison of generate -> execute -> refine pipelines at 1-3B scale, (b) an evolutionary (NEAT-inspired) search over constrained linear pipelines. Pipeline: generator -> executor (sandboxed subprocess, 10 s timeout, returns pass/fail and full traceback) -> optional analyzer (LLM diagnoses the traceback) -> refiner (gets problem, failed code, traceback, analyzer text) (Sec. 3.1, pp. 5-6). 1-3 refinement stages, each iterated 1-3 times; "early stopping" = the pipeline returns as soon as the code passes the tests. Models: gemma3:1B, qwen2.5:1.5B, llama3.2:3B in the search pool; qwen2.5-coder:3B only as a baseline; Ollama default Q4_K_M quantisation, 4096-token context, a single laptop (Sec. 3.1, 3.3, p. 9). Benchmarks: HumanEval (164) and sanitized MBPP (427 problems; note C14 uses 257). All headline numbers are 5-run means +/- SD, no fixed seeds; "sigma" is "a descriptive measure of separation between 5-run means relative to run-to-run variation ... rather than a formal hypothesis test" (Sec. 3.2, p. 8).

## Key results (with locators)
1. **Execution-feedback refinement helps a lot (Sec. 4.1, Tables 1-2, pp. 9-10).** llama3.2:3B solo 76.6 +/- 3.7 solved of 164 (46.7%) vs generate -> exec -> refine with the same model (3 iterations) 94.0 +/- 2.7 (57.3%): +17.4 problems (4.7 sigma). MBPP 255.8 +/- 5.5 of 427 (59.9%) -> 286.2 +/- 2.9 (67.0%): +30.4 (4.9 sigma). In percentage points: about +10.6 pp (HumanEval) and +7.1 pp (MBPP).
2. **Generator vs refiner (Sec. 4.2, Table 2, p. 10).** A 1.5B generator + 3B refiner (93.6 HumanEval, 287.0 MBPP) is indistinguishable from the 3B model doing both (differences -0.4 and +0.8 problems, 0.1 and 0.2 sigma). The refiner's capability mattered more than the generator's, provided the generator output is "close enough to repair".
3. **Error taxonomy (Sec. 4.3, Table 3, Fig. 2, pp. 10-11).** Fix rate ranges across configurations, HumanEval / MBPP: NameError 50-67% / 25-55%; SyntaxError 100% (small n) / 40%; TypeError 33-67% / 22-67%; AssertionError 4-24% / 7-35% ("Mostly unfixable"). Author warns rare categories (SyntaxError) are a pattern, not a precise ranking.
4. **Early stopping prevents regressions (Sec. 4.4, Tables 4-6, Fig. 3, pp. 11-13).** If every refinement iteration is forced (no stop on pass), the net value per iteration (new fixes minus new regressions) is negative in all four configurations: qwen->llama -6 / -7 / -22; llama->llama -7 / -9 / -13; NEAT champion -10 / -14 / -14; coder self-refine -7 / -10 / 0 (iterations 1/2/3; Table 4). Break rate of initially-correct code without early stopping (Table 6): 62% (qwen->llama; 43 of 69), 58% (NEAT champion; 45 of 78), 43% (llama->llama; 33 of 76), 14% (coder; 19 of 132). With early stopping, cumulative problems solved (Table 5, single run): llama->llama 76 -> 90 -> 92 -> 93 (iterations 0-3); qwen->llama 69 -> 91 -> 98 -> 99; NEAT champion 78 -> 96 -> 100 -> 102; coder 132 -> 136 -> 136 -> 136. Most of the gain arrives at the first iteration (14 of 17 for llama->llama; 22 of 30 for qwen->llama; 4 of 4 for coder). Tables 4-6 are single-run illustrations.
5. **Code-specialised model (Sec. 4.5, Table 1, p. 12).** qwen2.5-coder:3B solo 133.6 (81.5%) on HumanEval, 295.4 (69.2%) on MBPP; with self-refinement 139.6 (85.1%) and 307.2 (71.9%); +6.0 (1.4 sigma) and +11.8 (1.7 sigma), "suggestive". The coder pipeline beats the best general-purpose pipeline by +45.6 problems (12.4 sigma) on HumanEval and +20.2 (4.2 sigma) on MBPP; one refinement step was enough for the coder model, up to three helped the weaker general-purpose pipelines (Sec. 3.3, p. 9; Sec. 5.2, p. 15).
6. **Topology search (Sec. 4.6, Table 7, p. 13-14).** Three completed NEAT-style runs (+1 abandoned), population 20, fitness on 25-problem HumanEval subsets, space limited to linear pipelines, <=3 stages, 3 models. Two champions were the plain generate -> execute -> refine loop (v2: 93.8 +/- 3.3 vs the manual 94.0 +/- 2.7); one added an analyzer (v3: 98.2 +/- 3.4, +4.2 problems, 1.0 sigma, "not significant"). A deterministic-search champion validated at 89.8 +/- 5.2.
7. **Evaluation noise (Sec. 4.7, Table 8, pp. 14-15).** Single-run scores overstated 5-run means by 5.0-7.8 problems (HumanEval) (llama solo 82 vs 76.6; NEAT champion 106 vs 98.2). Search-time fitness (25 problems) did not rank champions reliably.
8. **Unfixable problems (Sec. 4.8, p. 14).** 7 of 164 HumanEval problems were never solved by any configuration (5 AssertionError logic problems; 2 NameErrors where every model hallucinated the same wrong identifier even though the traceback names it). All 427 MBPP problems were solved by at least one configuration in at least one run.
9. **Negative results, exploratory (Sec. 5.3-5.4, p. 16).** Text-only fan-out pipelines without verification vs a solo qwen2.5:3B: 1 win, 26 losses, 3 ties under Claude-judged pairwise evaluation. A heuristic-fitness-optimised text pipeline went 8-0-22 on the heuristic but 5 wins, 13 ties, 12 losses under Claude (Goodhart). Fine-tuning to distil the pipeline collapsed at sub-2B scale. The author states these were not evaluated systematically.
10. **Stated mechanism and limits (Sec. 5.1, 5.6, pp. 15-17).** Refinement helps "when the feedback is explicit, local, and machine-checkable". Limits: two easy benchmarks; Python only; 1-3B only; requires an execution oracle; hand-tuned parsimony penalty; population size 20; no fixed seeds; 5 runs is "still a small sample for precise confidence intervals".

## Verbatim quotes
1. (p. 11, Sec. 4.3) "The tracebacks provided by the executor give unambiguous signal for runtime errors but only symptoms for logical errors."
2. (p. 11, Sec. 4.4) "On already-correct problems, the refiner often makes the code worse."
3. (pp. 11-12, Sec. 4.4) "each additional refinement step is net-negative if forced, but cumulative success still rises when early stopping captures wins and prevents further damage."
4. (p. 15, Sec. 5.1) "refinement helps when the feedback is explicit, local, and machine-checkable. It helps much less when the signal only says the answer is wrong."
5. (p. 15, Sec. 5.2) "Always use early stopping. Without it, refinement was net-negative."
6. (p. 6, Sec. 3.1) "Early stopping means the pipeline returns immediately once execution passes."
7. (p. 17, Sec. 5.6) "The framework required an execution oracle, which limits the applicability of this strategy to domains with automated verification."

## Corrections to the current literature-review.md entry (C15)
Entry: "execution feedback mattered more than pipeline topology. Refinement fixes runtime errors but rarely logic errors. Early stopping was essential ('without it, every iteration is net-negative')." Informs: "stopping rules; logic bugs need semantic oracles." Route: Scite. Depth: abstract. "Preprint, 1-3B models."
- **"Early stopping" means "return as soon as the tests pass", not "stop when returns diminish".** The negative effect without it comes from re-running the refiner on code the oracle already accepts (break rates 14-62%, Table 6). It is therefore a gate on a pass/fail oracle, not an iteration cap or plateau detector. The review's synthesis ("cap iterations ... keep a best-so-far checkpoint") is a reasonable design response, but this paper tests only the gate: it never varies an iteration cap independent of the pass signal. The stronger lesson for a design loop is "do not apply a refinement step to an artifact the oracle has already accepted".
- **"Feedback mattered more than topology" rests on a bounded comparison:** NEAT-style search over linear pipelines with <=3 stages, 3 models, population 20, fitness on 25-problem subsets. The author calls the result "negative finding under our search regime" and does not claim topology is irrelevant in general. The "feedback vs no-feedback" contrast for code is solo generation vs generate-execute-refine; the no-feedback pipelines were run only on text tasks (not systematically evaluated). There is no code arm in which refinement runs without the traceback.
- **"Rarely fixes logic errors":** supported (AssertionError fix 4-24% HumanEval, 7-35% MBPP) for 1-3B models only. C14 reports about 45% (HumanEval) and about 63% (MBPP) for 8B-70B+ models, so the logic-error repair rate rises with model capability; do not carry the 1-3B figure to frontier models.
- **Missing:** the traceback also helps only when the model can act on it; refiner capability mattered more than generator identity; a code-specialised 3B model outperformed all general-purpose pipelines by a larger margin than any pipeline change (+45.6 problems on HumanEval vs +17.4 for refinement).
- **Missing:** 5-run means with no fixed seeds; "sigma" is descriptive; single-run scores overstate by 5-7% (relevant to any single-trial claim).
- **Check:** the quoted sentence is in the abstract as "Early stopping is essential; without it, every iteration is net-negative." The review's quote is accurate.
- Benchmarks: MBPP here is the 427-problem sanitized set (C14 uses 257); Python only; Q4_K_M quantised local models.

## Design relevance
- **Gate refinement on a failing oracle.** In the Gaia loop, a "refine" step should run only when an explicit check fails (compile/type error, exception, failed world-state assertion). If the check passes, stop and checkpoint; extra "polish" iterations on an accepted state broke 14-62% of already-correct solutions here. Keep the last passing snapshot to roll back to if a later edit regresses.
- **Specific, local, machine-checkable feedback is what works** (NameError/SyntaxError fixable, bare AssertionError not). This supports surfacing F# compiler and runtime diagnostics verbatim, adding named assertions over world state (entity exists, position within bounds, count equals), and returning "expected vs actual" with the failing assertion's name, rather than relying on the model to judge from a screenshot alone.
- **Subjective design quality has no such oracle,** so expect the repair loop to help with "does it run / does it satisfy the stated property" and not with "is it good". This paper offers no evidence for visual or gameplay-quality refinement.
- **Refiner capability over generator:** the model that applies the repair should be the strongest available; cheap models may draft probes, but the repair step benefits from capability.
- **Mind the noise floor:** a single trial overstated scores by 5-7%; evaluating the Gaia agent on a handful of design tasks needs repeated runs.

## Limits / credibility
- Preprint, single independent author, no peer review; credibility-gate label: `context_or_prior_art_only`.
- Scope: 1-3B models (local, quantised), Python, HumanEval/MBPP only, execution oracle required; main claim is about a narrow search space. Results at 7B+ or on harder tasks are explicitly "an open question".
- Several comparisons are at 1-1.7 sigma and are labelled "suggestive" or "not significant" by the author; the text-pipeline and fine-tuning negative results are exploratory.
- No funding or conflict statement in the text I read.
