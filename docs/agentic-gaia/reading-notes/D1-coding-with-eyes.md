## What the paper is
(i) **InteractGUI Bench**: 984 desktop-GUI app-reconstruction tasks built from Flathub "Popular" screenshots (1,200 candidates, 984 kept; 2,027 screenshots, mean 2.06 per task; icons/images masked), with Gemini-3-Flash-generated metadata, instructions and an "Interactive Evaluation Script" (IES, YAML: assert element / assert color / assert layout; click / input text / dropdown) executed on the running PySide6 app through Linux AT-SPI (accessibility tree). Colour assertions use pixel RGB distance d < 80. Layout is scored by a purpose-trained dual-stream ResNet-50 similarity model ("visual score", MAE 0.09 on its own synthetic test set of 25k pairs). (ii) **VF-Coder**: a three-agent system (Task Planner, GUI Operator, Code Fixer). The GUI Operator launches the app in a sandbox, sees a screenshot plus stdout/stderr logs plus the reference screenshot each step, and drives the mouse/keyboard through a computer-use tool; on a suspected bug it terminates and reports; the Code Fixer receives the bug description, the reference screenshot and the screenshot captured at failure time and edits through SEARCH/REPLACE blocks (Sec. 4, App. E.2).

## Key results (with locators)
1. **Single-shot baselines (Table 1, p. 11).** % Resolved (all IES steps pass), PySide6: GPT-5.2 26.99; Gemini-3.1-Pro 23.57; Claude-4.5-Sonnet 23.18; Gemini-3-Flash 21.68; Kimi-2.5 11.31. Avg. visual score 0.4839 / 0.4816 / 0.3378 / 0.4284 / 0.3867. Fail-to-start (FS) 14.5-27.1%. Avg cost per task $0.0147 (Gemini-3-Flash) to $0.2076 (Gemini-3.1-Pro).
2. **VF-Coder vs text-agent frameworks, Gemini-3-Flash backbone (Table 2, p. 12).** Baseline 21.68% / visual 0.4284 / cost $0.0147 / FS 25.20 / AE 49.05 / AC 58.35 / CK 58.62. +Gemini CLI 24.81 / 0.5190 / $0.1309 / FS 7.14. +Cursor CLI 25.46 / 0.5028 / $0.1726 / FS 1.59 / CK 73.64. +VF-Coder 28.29 / 0.5584 / $0.2064 / FS 4.47 / AE 58.41 / AC 75.93 / CK 71.33. Gain over baseline: +3.13 (Gemini CLI), +3.78 (Cursor CLI), +6.61 (VF-Coder) points. Cost is about 14x the single-shot baseline and about 1.2x to 1.6x the text-agent frameworks. Cursor CLI beats VF-Coder on click success (CK 73.64 vs 71.33) and on fail-to-start (1.59 vs 4.47).
3. **Ablation (Table 4, p. 13).** Without the GUI Operator (text-only debugging and fixing): 24.79% / visual 0.5193 / $0.1351. With visual debugging but text-only fixing ("w/o bug screenshot"): 27.64% / 0.5390 / $0.1963. Full (visual debugging and the failure screenshot to the fixer): 28.29% / 0.5584 / $0.2064. So within the same pipeline, vision adds 2.85 points at the debugging stage and 0.65 at the fixing stage (+3.50 total over the text-only pipeline); the non-visual three-agent pipeline itself already adds +3.11 over the single-shot baseline. The paper itself says bug screenshots "have limited utility for other types of errors such as functional logic".
4. **Kimi comparison (Table 3, Sec. 5.2).** Manual evaluation on an 80-app subset (the Kimi agent has no public API; screenshots and prompts were uploaded to its web interface): Kimi-K2.5 16.25 -> +Kimi Agent 18.75 -> +VF-Coder 25.00 % Resolved. On 80 apps these are 13, 15 and 20 apps; visual score is higher with the Kimi Agent (0.5648) than with VF-Coder (0.5530).
5. **Extra benchmarks (App. B).** Design2Code-Hard (80 examples, Gemini-3-Flash): VF-Coder is best on Position (88.15) and Color (89.09) but within 1.8 points of "Direct" on every metric and below "Self-Revision" on Block (77.83 vs 78.09), Text (96.31 vs 98.65) and CLIP (91.07 vs 91.28; Direct 90.64). WebGen-Bench (101 tasks, 647 test cases, judged by Gemini-3-Flash, the same model as the backbone): VF-Coder repair on top of Bolt.diy codebases raises accuracy 31.8% -> 41.8% and appearance 2.74 -> 3.96, "Start Failed" unchanged at 14.7%. This is a repair stage added after generation, so compute is not matched.
6. **Operational parameters (Sec. 5.1).** Task Planner capped at 10 planning iterations; the GUI Operator at 5 steps per subtask with only the 4 most recent interaction histories retained; the framework terminates at the step limit; Operator and Fixer histories cleared after each subtask. Operator prompt rules (Fig. 15): one action per step, never predict multiple clicks; do not repeat an identical action more than twice when the screenshot does not change (treat as a bug); report full log errors.
7. **Visual evaluation model (Sec. 3.2, App. D).** Trained on 25k synthetic pairs (Gemini-3-Flash HTML reconstructions of 2,048 benchmark interfaces plus 484 Design2Code pages, ten procedural variants each; scale +/-30% labelled 1.0, deletion/shift/collapse variants penalised linearly, random other-app pairs 0). Best validation MAE 0.0964 (epoch 18). Fig. 8-9 are qualitative; no human-agreement study is reported, although Table 5 rates the benchmark "High" for human alignment.
8. **Error analysis is qualitative only** (Sec. 5.4, Fig. 4): all methods "still exhibit visible gaps compared to the Real UI Screenshots".

## Corrections to the current literature-review.md entry (D1)
Entry: "text-only feedback is weak for event-driven, visual GUI programs. A multi-agent system that interacts with the running UI and inspects visuals raised Gemini-3-Flash's success from 21.68% to 28.29% (visual score 0.428 to 0.558). Modest absolute gain." Depth: "abstract (Scite and WF)".
- The numbers (21.68 -> 28.29; 0.4284 -> 0.5584) are correct, but attributing the whole +6.61 points to visual feedback is not supported. A non-visual version of the same pipeline already reaches 24.79% (+3.11), the same as the text-only Gemini CLI (+3.13) and Cursor CLI (+3.78) frameworks. The visual increment measured inside one pipeline is +3.50 points (24.79 -> 28.29), of which +2.85 comes from the screenshot-driven GUI Operator and only +0.65 from showing the failing screenshot to the code fixer. Suggest wording: "visual interaction added about 3.5 points over an equivalent text-only agent pipeline (24.8% -> 28.3%); the whole stack is +6.6 over single-shot".
- "Informs: visual plus interaction feedback" should be split: what helped was *interactive exploration with screenshots to find bugs* (detection), not screenshots as input to the fixer (repair, +0.65 points).
- Missing: cost (about 14x the single-shot run: $0.2064 vs $0.0147 per task; about 1.2-1.6x the text agents) and iteration caps (10 planner iterations, 5 operator steps per subtask).
- Missing: the "visual score" is from a ResNet-50 similarity model trained on synthetic perturbations, with no reported human validation; instructions and IES were also generated with Gemini-3-Flash, which is the backbone in the headline comparison.
- Missing: extra-benchmark evidence is mixed (Design2Code-Hard: within about 2 points of the "Direct" baseline on every metric; WebGen-Bench: +10 points accuracy but judged by the same model and with extra repair compute).
- Venue: none claimed; the Kimi comparison is a manual 80-app subset.

## Design relevance
- **Value of looking is in finding problems, not in fixing them.** Screenshot-driven exploration added +2.85 points; giving the fixer the failing screenshot added +0.65. For Gaia: put the effort into a cheap way for the agent to observe state at the moment of failure (frame, world diff, log), and make sure the *reported* finding is textual and specific ("the Download page is blank", "Back to Home button missing") for the editing step.
- **Interaction, not a single static image.** The GUI Operator clicks through the app along the task's navigation path with a screenshot after each action, and also receives stdout/stderr. For an editor with a live game, the analogue is "drive an input script, advance time, capture"; logs should accompany images (the operator prompt requires reporting log errors verbatim).
- **Small hard caps and a no-progress rule.** 10 planner iterations, 5 UI steps per subtask, 4-step history window, and "same action twice with an unchanged screenshot = bug, stop" are concrete limits that worked at a cost of about $0.2 per task. These are directly usable defaults for the Gaia screenshot/advance loop.
- **Matched controls matter.** Compare any Gaia visual-feedback claim against a text-only agent with the same loop structure; here half of the apparent "visual" gain was loop structure.
- **Sandboxed accessibility-tree assertions.** The evaluation used AT-SPI element queries for presence/click assertions and pixel checks for colour: structured state first, pixels second. This matches the review's recommendation to pair screenshots with structured world state.

## Limits / credibility
- Preprint v1, no venue claim; credibility-gate label: `context_or_prior_art_only`.
- Single backbone for the headline (Gemini-3-Flash), 984 tasks, number of runs not stated, no confidence intervals. At about 28% and n = 984 the binomial standard error is about 1.4 points (my calculation), so the 0.65-point fixer effect is within noise and the 2.85-point detection effect is about two standard errors.
- Evaluation and training of the visual metric are self-built; the benchmark's own task and test generation used the same Gemini-3-Flash model that the method uses.
- Desktop PySide6 app reconstruction from screenshots, not interactive game editing; no time-evolving scenes; the "visual feedback" is a static screenshot after discrete UI actions.
- Competing agent comparisons use default configurations of different products (Gemini CLI, Cursor CLI), so differences include harness differences beyond vision.
