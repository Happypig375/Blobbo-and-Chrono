## What the paper is
A Godot 4 benchmark (v2: 333 tasks = 154 "core" tasks plus 179 variants, built from 57 video and 31 web tutorials with GPT-5-based task construction, an agentic refinement pass, and review of all tasks by 8 human annotators, 5 with game-development experience; Sec. 2). Each task provides a project folder and an instruction; success is a deterministic Godot GDScript test of scene state or behaviour (no LLM judge). Agents run in their native CLI harness (claude-code, codex, gemini-cli) or OpenHands, and solve tasks by editing files ("evaluate agents that attempt to solve tasks through code generation alone", Sec. 3.2). Two feedback add-ons are compared (Sec. 4.1): (1) **Editor Screenshot MCP**, an MCP server with one tool `godot-screenshot` that loads the Godot editor for the task and returns a screenshot of the editor (scene view, node tree, inspector); (2) **Runtime Video**, which is a prompt addition telling the agent how to record gameplay with Godot's `--write-movie` (a still frame or a short AVI), after which "models process videos into image frames using python" themselves. The baseline prompt already says "You are a visual agent and can use images and videos to help you understand the state of the game."

6. **Failure analysis (Sec. 4.3, App. G, I, Tables 6-7).** Top-4 configurations, LLM-judged, non-exclusive: missing or mis-parented nodes 63.4%; missing method/property/signal 36.2%; unset exported reference 35.9%; incorrect physics setup 32.1%. Multimodal-grounding failures: incorrect shader/material assignment 22.6%, shader/post-processing/environment parameters 22.6%, UI layout/spacing/anchoring 19.9%, wrong animation state/direction/frame sequence 17.8%, camera framing 17.1%, spritesheet region 15.3%. Example (App. G): GPT-5.4 puts `sub_emitter` on the wrong resource.
7. **Task quality and contamination.** Of 41 auto-generated tasks reviewed by humans: 43% issue-free, 50% minor issues, 7% major (Sec. 2.3); human review under 10 minutes per task; the paper's own contamination check (App. J, ROUGE-L about 0.06, BLEU-4 about 0.017 on transcript continuation for two models) finds no evidence of systemic memorisation of tutorial transcripts. Reference solutions average 4.7 files and 114.1 lines changed; 82.4% of tasks include non-code assets (Sec. 3.2).
8. **Statistics.** Single reported pass@1 per cell; the number of runs per configuration, confidence intervals and significance tests are not stated in v1 or v2.

## Corrections to the current literature-review.md entry (A1)
Entry: "Godot tasks from tutorials. Agents solve about half (v1: 54.5% of 132; Z-note v2: 53.8% of 333). Success drops from 46.9% on gameplay tasks to 31.6% on 2D graphics. Two simple feedback tools consistently improve performance. One is an Editor Screenshot MCP that returns an editor screenshot (scene, node tree, inspector). The other is runtime video. Claude Sonnet 4.5 rose from 33.3% to 47.7%." and "Spot-check (Opus, Scite excerpts): for Claude Sonnet 4.5, runtime video 33.3% -> 41.7%, screenshot MCP alone no improvement, both combined ~ best single method." Route: "Scite + Zotero ... Depth: abstract (Scite, v1) + 5 excerpts + Z-note (v2/PMLR)".
- **Version mixing.** 46.9% / 31.6% / 33.3 -> 47.7 are v1 (132 tasks) numbers; the 333-task v2 gives 51.4% / 33.0% and a different headline (GPT-5.4 41.1 -> 52.0; Sonnet 4.5 28.8 -> 34.8 with both arms). The entry should label which numbers belong to which version, and prefer v2 (the ICML proceedings version).
- **Resolved spot-check question ("which configuration produced 47.7% was not in the excerpts").** In v1 Table 2, 47.7% is Sonnet 4.5 with video only; the "41.7%" in the v1 prose and in the spot-check is a text/table mismatch in v1 (Table 2 and the abstract say 47.7). The substantive finding stands and is stronger than the spot-check phrased it: video-only +14.4 points, screenshot-only 0.0, both +12.9.
- **Generalisation.** The review's synthesis ("for Claude Sonnet 4.5 the gain came from runtime video, not the editor-screenshot MCP") is a one-model statement from v1. Across the 5 (v1) and 3 (v2) models with isolated arms, runtime video is the larger or equal single-arm gain in all but one cell (v1 Gemini 3 Flash: screenshot-only +3.8 vs video-only +1.5); screenshot-only gains range -0.8 to +3.8. In v2 Sonnet 4.5 has no isolated arms, so the Sonnet claim cannot be checked there.
- **What "runtime video" is.** It is a prompt-level instruction to run Godot's movie writer, not a tool; the agent itself extracts frames with scripts. The "editor screenshot" is a tool that launches the Godot editor for the task and returns one image (static, not an interactive editing session). The two arms therefore differ in delivery mechanism as well as in modality; the paper does not separate these.
- **Not a test of editor-driving.** Agents solve tasks by editing files ("code generation alone"), so the screenshot arm is "look at the editor" and not "operate the editor". The review's phrase "closest to our design" is true for the screenshot tool shape, not for agent-in-editor control.
- **Missing**: costs (up to 3.3x for GPT-5.4), harness sensitivity (30.3 vs 45.4 for the same model), no run-to-run variance or CIs reported, v2's easy/hard split and contamination check.
- **Depth/venue**: now full text, v2 (and v1 partly); venue verified as ICML 2026 PMLR 306:19395-19423.

## Design relevance
- **Which visual channel helped: motion/camera output, not the editor view.** In both versions the arm that yields the most is runtime video (a recorded run of the game, which "captures both temporal elements ... and the current camera view (the editor does not show the camera view)"), and the editor screenshot adds 0 to about 4 points on its own. This supports the planned frame-sequence tool over relying on an editor screenshot, and it supports treating editor screenshots as the secondary channel. Caveat: the benchmark's editor screenshot is mostly redundant with `.tscn` text that agents can read; a screenshot of a live game editor view would add more only where layout is not in text.
- **Combined access can be worse than the best single channel.** In v2 all three isolated-arm models score below video-only when given both channels (e.g. GPT-5.4 mini 39.0 vs 43.2; Gemini 3 Flash 44.1 vs 46.9), and the authors call this "surprising". Keep the number of feedback tools small and make the default one the runtime-frames tool; do not assume more channels help.
- **Gains are model- and harness-dependent and sizeable for some models only.** +10.9 points for GPT-5.4 (both), +6.0 for Sonnet 4.5 (v2) but -1.3 for Gemini 3 Flash (both) and negligible for Qwen. Evaluate Gaia tools on the actual model, not on a generic claim.
- **Cost is part of the design.** GPT-5.4's cost went up 3.3x with feedback, mostly from tokens spent on frames; a contact-sheet tool that compresses many frames into one image targets this directly (hypothesis, not tested here).
- **Deterministic state checks as the oracle.** All tasks are verified by in-engine unit tests of scene and behaviour (e.g. "checking animation states at each frame"); the benchmark deliberately avoids LLM judges. Gaia's eval/world-inspection tools provide the same kind of oracle and should be reported separately from visual feedback.
- **Prompt text used in the feedback arms** is short and procedural ("use screenshots before starting ... after making changes ... during debugging"; the exact `godot --write-movie` commands with `timeout`); useful as a template for tool descriptions.

## Limits / credibility
- Peer-reviewed at ICML 2026 (proceedings entry verified); credibility-gate label: `eligible_for_claim_subject_to_article_appraisal` for the benchmark and for the within-benchmark feedback comparison, not for transfer to editor-driving agents or to F#/Nu.
- Single pass@1 per configuration, no CIs. At 132-333 tasks and success rates of 30-50% the binomial standard error of one rate is about 2.7 to 4.3 points (my calculation, unpaired), so single-arm differences below about 5 points (most screenshot-only effects) cannot be distinguished from noise; the large gains (GPT-5.4 +10.9, Sonnet 4.5 +14.4 in v1) are larger than that.
- Tasks derive from tutorials (localised edits with in-engine tests), created by GPT-5-family agents and then human-reviewed; models used for task generation (GPT-5/Codex) overlap with evaluated families. The authors' contamination check covers transcripts only.
- Arms differ in mechanism (prompt instruction vs MCP tool), not just modality; the harness differs by model, so cross-model comparisons mix model and harness.
- Models changed between versions, so v1 and v2 results are not directly comparable; the task set tripled.
- Godot only; code-editing agents, not GUI-driving; the paper states Godot "strongly resembles Unity", no evidence for other engines.
