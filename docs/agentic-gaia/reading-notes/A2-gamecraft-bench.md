## What the paper is
A 140-task Godot 4 benchmark (15 game families, 12 annotators; Table 3) in which an agent must build a complete game project from a natural-language, product-style specification and also write 1-10 JSON input traces (timed mouse/keyboard events) that demonstrate the game (Sec. 3.1-3.2). The verifier (i) gates on launchability (`BUILD = 0` zeroes the score), (ii) replays each trace in a fresh Godot instance at 1280x720, 30 fps, records video (stored at 854x480), samples frames every 0.5 s from at most a 20 s window, and (iii) has a multimodal judge (GPT-5.5) score the frames against a hidden rubric (at most 24 items) in four categories: Core Mechanics (M), Content Depth (D), Functional Visuals (V), Art and Presentation (A) (Sec. 3.2, App. A). Score = BUILD x (0.15 M + 0.35 D + 0.15 V + 0.35 A). Agents may "run the project, inspect screenshots, and iterate from tool feedback"; a `screenshot.sh` helper is provided in the task instructions (App. C). Agent timeout 7,200 s, verifier timeout 1,800 s, no explicit tool-call cap (App. A).

## Key results (with locators)
1. **Main scores (Sec. 4, Table 4, p. 10-11).** Overall: Opus-4.7 high (Claude Code) 41.46; GPT-5.5 high (Codex) 39.49; Kimi-K2.6 (Kimi Code) 30.65; MiMo-V2.5-Pro (Claude Code) 24.10; GLM-5.1 (Code Buddy) 18.29; MiniMax-M2.7 (Code Buddy) 10.95; DeepSeek-V4-Pro (Codex) 2.15. One run per task and configuration; seven agent-model combinations, so harness and model are confounded.
2. **Category pattern (Sec. 4, Table 4).** Mechanics > Content Depth for the top three (Opus 55.34 vs 39.48 D, GPT-5.5 54.36 vs 38.61, Kimi 39.76 vs 28.07). Visuals 42.78 / 41.84 / 33.66; Art 36.86 / 32.94 / 27.99. "Findings 1": agents produce recognisable local mechanics but fail to assemble complete systems. Note the aggregate weights Depth and Art at 0.35 each by design, and the rubric text caps scores at 0.5 when assets are programmatic shapes or default widgets (App. C, Strategy-Skirmish `rubric.json`: "Score 0.5 at most if the mechanic works but is represented entirely by programmatic shapes ..."), so lower D and A scores are partly built into the rubric rather than purely measured.
3. **Delivery-contract failures (Sec. 4, Fig. 6, Sec. 5.1).** Build pass rates are high for most agents (about 91-100%), but DeepSeek-V4-Pro has a valid-trace rate of only about 25.6% against a build pass rate of about 93.2%, explaining its 2.15 score ("often ignores or violates the demonstration-trace requirement"). For MiMo-V2.5-Pro all five zero-score tasks "produced a valid build but submitted no demo traces". So part of the low-score mass is non-compliance with the evidence protocol, not game quality. Average demos per task range from 1.27 (DeepSeek) to 9.11 (GLM-5.1); demo duration 13.0 to 19.1 s.
4. **Visual feedback usage (Sec. 5.1 "Success Signal", Fig. 7, Findings 2).** Count of "rendered-screen inspections" via the helper: Kimi-K2.6 2,998 over 140 tasks (21.41 per task, median 19; only 4 tasks use none); Opus-4.7 1,952 (13.94 per task); GPT-5.5 268 (1.91 per task). Evidence offered: one qualitative case (Kimi on Strategy-Skirmish debugging unit placement, missing selection highlights, grid and turn-indicator layout; overall 39.33) and these counts. There is no ablation (no no-screenshot arm), no analysis of score vs screenshot count, and the counts do not rank with scores: GPT-5.5 used about one-tenth as many screenshots as Opus and scored 39.49 vs 41.46, and Kimi used the most and scored 30.65. "Findings 2: Rendered interaction helps agents debug failures that are not observable in source code" is therefore supported by a case study, not by a controlled comparison.
5. **Effort is decoupled from quality (Sec. 5.1 "Failure Signal", Fig. 8, Findings 3).** MiMo-V2.5-Pro: shell commands 56.3% of tool calls, Read + Edit 16.5%, median 128 tool calls per task, correlation of score with total tool calls r = +0.016. "The bottleneck is structural rather than raw effort."
6. **Judge reliability (Sec. 5.2, Fig. 9, Table 5, Findings 4).** Stability: GPT-5.5 judge re-run 10 times on fixed evidence from two families (Simulation, Card Game) for four agents; per-family score SD 0.0036-0.0050 (Kimi 0.0037 / 0.0038, Opus 0.0050 / 0.0036). Human calibration: Kimi-K2.6 submissions from three families (Card Game, Idle, Racing); overall human 22.69 vs judge 26.02 (judge +3.32); category deltas (judge minus human): M +1.92, D +5.38, V -5.87, A +5.80; family deltas: Card Game -0.27, Racing +2.38, Idle +8.76. The authors say it "is small and is not designed to estimate inter-annotator agreement" (number of human raters and items not stated in the text). Judge identity: GPT-5.5, which is also the second-ranked evaluated agent (self-preference not discussed beyond a generic "judge-model bias" remark in Limitations).
7. **Category coupling (Sec. 5.3, Fig. 10, Findings 5).** Kimi: M-D r = 0.61, M-V 0.53, V-A 0.11; MiMo: A vs M, D, V r = 0.56, 0.39, 0.26. Capability is "partially factorized".
8. **Benchmark-design claims (Sec. 2-3).** Three desiderata (engine grounding, artifact completeness, interactive verification); replay traces are submitted by the agent so that the verifier need not explore ("turning verification into an autonomous exploration problem"). Godot was chosen for being open-source, headless-friendly, and text-based; Unity/Unreal are described as heavier, editor-centric, binary-format (Table 2). Task QC: each task has an annotator-written oracle (a minimal playable Godot sketch) to check that the spec is implementable and every rubric item corresponds to an observable state (Sec. 3.4). Table 1 compares only against GameDevBench, OpenGame-Bench and WebGameBench.
9. **Scope limits stated (Limitations, p. 16).** 2D Godot only; no 3D, multiplayer, long-form production; visual evidence only (no audio); relies on a multimodal judge ("judge-model bias, API drift, or limitations in visual understanding"); does not measure fun.

## Corrections to the current literature-review.md entry (A2)
Entry: "140 Godot tasks. Agents must deliver replayable demonstration traces. A multimodal judge scores sampled gameplay frames (2 fps) against hidden rubrics. Mechanics scores exceed content and presentation scores. The authors argue many failures 'only become visible after rendering' and that without visual feedback 'an agent may continue editing code while remaining blind' (a claim, not an ablation)." and "Route: Scite. Depth: excerpts (5; the abstract is only a figure caption)."
- Everything stated is accurate; the "(claim, not an ablation)" caveat is confirmed. Additional nuance now available from the full text: the supporting evidence is a screenshot-call count and one case study (Kimi), and across agents the count does not track score (GPT-5.5: 1.91 per task, 39.49; Kimi: 21.41 per task, 30.65). A stronger statement than the review's is warranted: the paper contains no evidence that more screenshots yield higher scores.
- "Mechanics scores exceed content and presentation scores" is true but partly rubric-induced: the rubric caps Content Depth and Art items at 0.5 for placeholder/programmatic art, and D and A carry 0.35 weight each.
- Missing: much of the low score mass is protocol non-compliance (no valid replay traces: DeepSeek-V4-Pro valid-trace rate about 25.6%; MiMo's five zero-score tasks), not poor game quality.
- Missing: the judge is GPT-5.5, one of the agents evaluated; judge stability SD about 0.004-0.005 on fixed evidence; human calibration is a small preliminary check on one agent's outputs (Kimi-K2.6, three families) with judge +3.32 points more permissive overall and up to +8.76 on Idle. Replace any impression that the judge is validated against human raters.
- Missing: best score 41.46% (Opus-4.7 high), second 39.49% (GPT-5.5 high); seven agent-model combinations, so "harness" is confounded with model.
- Venue: no venue claimed (cs.CL preprint v1). The review gives none, which is correct.

## Design relevance
- **Evidence format worth copying: agent-authored deterministic scenarios.** Each game accepts `--scenario <id>` to jump to a named state deterministically (seed RNG, skip menus), and a trace is a frame-indexed list of input events. For Gaia the analogue is a recorded input script plus a named world snapshot, replayed with "advance N ticks and capture" to produce a contact sheet. Replay removes dependence on the verifier's own exploration.
- **Sampling choices that were actually used for the judge:** 2 frames per second, at most 20 s (about 40 frames) per demo, 854x480 stored video, up to 10 demos per game. A contact-sheet tool of that scale is credible for an LLM judge; the paper does not say whether lower or higher rates change judge accuracy.
- **Screenshot helper design (App. C).** `screenshot.sh --path <project> -- --out <png> --frames <N> [--scenario <id>]`: run headless for N frames, then save a PNG, with an optional scenario to land in a specific state. It is a single-purpose tool with explicit instructions to use it "to actually see" the UI. This is the closest published analogue of the planned screenshot tool, but the paper does not test whether it helps.
- **Do not equate screenshot volume with progress.** Tool-call volume (r = +0.016) and screenshot count showed no relationship with score, so frame budgets and a "look, then act on what was seen" prompt are more important than encouraging more looks.
- **Evaluation hygiene:** an agent-supplied demonstration can stage a favourable state; the authors counter with max-vs-mean aggregation and a strict rubric. For Gaia evaluation, staged states should be defined by the harness, not the agent, or the check should be state assertions rather than a frame judge.

## Limits / credibility
- Preprint v1; credibility-gate label: `context_or_prior_art_only`.
- Single run per cell; judge is a single proprietary model (GPT-5.5) that is also an evaluated agent; the rubric is hidden but annotator-authored with oracle sketches only as a feasibility check; no inter-annotator agreement.
- Evaluation is visual only (no audio), 2D Godot only, no human play-testing, "does not measure whether a generated game is subjectively fun".
- No feedback ablation, so it cannot support a claim about which visual channel helps; it does show agents can and do use a screenshot helper.
- Industry co-authors (Tencent Hunyuan) alongside academic groups; no funding conflict stated in the text I read beyond grant acknowledgements.
