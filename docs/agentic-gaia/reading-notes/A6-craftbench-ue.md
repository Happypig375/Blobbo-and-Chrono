## What the paper is
An Unreal Engine 5.8 (Windows) evaluation harness plus a 70-task benchmark: 33 C++ tasks, 25 Blueprint (BP) / native-asset tasks, 12 editor-scripting (Python) tasks (Sec. 3.4, Table 1). The agent works in an isolated project; its saved changes are copied into a fresh project and graded with three deterministic gate types (Sec. 3.3): L1 build, L2 behaviour (fixed-timestep Play-in-Editor session with named assertions via Unreal Functional Tests; `-deterministic -FPS=60`, 1/60 s step, per-task tolerances; App. B), L2I artifact inspection (load saved assets headless and check graph topology, class hierarchy, typed properties, references, persistence). No LLM reads the submission, trace, screenshot or report. Seven models (Claude Sonnet 5, DeepSeek V4 Pro, Gemini 3.7 Flash, GPT-5.6 Luna, GPT-5.6 Sol, Grok 4.6, GLM-5.3 Flash), all driven through Claude Code, one attempt per task x model x configuration, pass@1 with a 40-minute authoring budget (60-minute ceiling) (Sec. 4.1-4.2; non-Anthropic models are routed through OpenRouter's Anthropic-compatible endpoint, App. B). Two editor-tool configurations: MCP1 ("Unreal MCP") and MCP2 ("Aura MCP"), plus a file/shell baseline on C++ tasks. Task validity gates: reference solution must pass and the unchanged project must fail; verifier sources withheld and exposure monitored (Sec. 3.5, Fig. 2, App. B.1).

## Key results (with locators)
1. **Overall completion (Sec. 5, p. 6; Fig. 5, Table 6, App. C).** C++: 180/231 (77.9%) file/shell, 199/231 (86.1%) MCP1, 203/231 (87.9%) MCP2. BP: 110/175 (62.9%) under both MCPs. Python: 62/84 (73.8%) MCP1, 66/84 (78.6%) MCP2. Per-model BP range (Table 6): 44.0% to 76.0% (MCP1) and 32.0% to 76.0% (MCP2). Claude Sonnet 5: C++ 27/33 baseline, 30/33 MCP1, 30/33 MCP2; BP 19/25 and 17/25; Python 11/12 and 9/12.
2. **Paired C++ vs Blueprint on the same ten gameplay specs (Sec. 5.1, Tables 3, 7, 9, Fig. 3).** C++ completion 46/70 (65.7%) MCP1 and 50/70 (71.4%) MCP2; BP 25/70 (35.7%) and 20/70 (28.6%); gaps 30.0 and 42.9 pp. File/shell baseline already 45/70 (64.3%) on the paired C++ tasks. Every model completes more C++ than BP versions. Counting BP runtime passes without the asset checks leaves all four counts unchanged (Table 9): no on-time BP submission passes runtime but fails assets, so the gap is not an artefact of the extra asset checks. Successful C++ submissions only change C++ source, successful BP ones only change assets.
3. **Where the editor MCP helps (Table 8, Sec. 5.1).** On the 23 C++ tasks without BP counterparts: 135/161 (83.9%) baseline vs 153/161 (95.0%) for each MCP. On the ten paired C++ tasks: 45/70 vs 46/70 vs 50/70. So most of the MCP advantage on C++ is on the non-gameplay-pair tasks. For all seven models median C++ authoring time is longer with either MCP than with the baseline (App. E, Fig. 7). Per-model C++ effects are mixed (GLM-5.3 Flash 26/33 baseline falls to 23/33 under MCP1; Table 6).
4. **BP difficulty by task type (Sec. 5.1, Fig. 6).** Basic graph ops 100.0% / 95.2% (MCP1 / MCP2), local repair 92.9% / 100.0%; the five together 34/35 (97.1%). Asset-configuration 72.9% / 80.0%. Gameplay 35.7% / 28.6%. "Agents often complete the included local operations, while fewer submissions implement all parts of a gameplay feature correctly."
5. **Structure-valid is not behaviour-valid (Sec. 5.2, Tables 13-14, App. D.3).** Final (including late) BP gameplay submissions that pass asset checks but fail an explicit runtime assertion: 24/70 (34.3%) MCP1, 28/70 (40.0%) MCP2. Among on-time submissions passing the asset checks: 19/45 (42.2%) and 20/40 (50.0%). So the headline percentages (and the review's "42.2% and 50.0%") are on-time subsets of the ten paired BP gameplay tasks only. Failure categories (Table 13): required effect or resource use (8 / 6), pose/display/indicator (5 / 8), restoration/preserved behaviour (5 / 6), initial Health or Power (3 / 4), poison damage ratio (3 / 4). Thirteen submissions across four tasks activate an ability but miss its effect; seven concern the glide task: all seven abilities activate, six consume Power, none produce the required glide (p. 8; App. D.3 cautions that no common mechanism is established).
6. **How agents inspect and verify (Sec. 5.3, Table 4, App. D.1, Table 10).** BP runs (175 per MCP): task-asset readback 149 (MCP1) / 165 (MCP2); compilation request 131 / 132; PIE start request 38 / 44; PIE state readback 24 / 30; image-capture request 15 / 10 (only 7 / 8 runs have an image actually returned into the conversation). C++ shell commands that run the game or engine tests: 57/231 MCP1 and 39/231 MCP2. Per-model BP PIE starts (Table 10, out of 25 runs): Sonnet 17 / 18, GLM 14 / 13, DeepSeek 4 / 6, Sol 0 / 0. The prompt told agents to perform at most one PIE playtest, added "after observing repeated playtest loops in preliminary runs" (Sec. 4.2); the limit is not enforced. The paper does not test whether more runtime checking would help; it only observes that asset readback is far more common than runtime readback. In ten BP runs under MCP2 and five under MCP1 the agent read a value in PIE and still failed final runtime checks ("Reading a value during PIE can leave other required behaviors untested").
7. **Edit-error recovery (Sec. 5.3, App. D.1, Tables 11-12).** In 175 MCP1 BP runs, 95 write graphs directly (454 writes); 58 have a graph-writing error and 37 changed the same graph in their next call. 30 of 94 runs with accepted writes later revised those graphs. In 39 on-time runs where every graph-write error was followed by a changed, error-free request for the same graph, 16 still failed the final evaluation (15 on runtime assertions, six models, eight tasks). Five MCP1 BP submissions have unresolved resource references (class-qualified names the engine cannot resolve; App. D.2) and also fail runtime checks.
8. **Tool-surface size and cost (App. B, App. E, Table 15).** MCP1 exposes 3 entry points (catalog discovery, tool description, a gateway that calls a named operation); MCP2 exposes 176 direct entry points. On matched C++ prompts the median first-request input is 3.99x larger under MCP2 (median +82,354 tokens). Median paired MCP2/MCP1 billed-cost ratio 1.80-2.69x for five models, 0.21x for DeepSeek (cache effects: 3.47% vs 98.21% of input served from cache); Claude Sonnet 5 has no billing linkage (0/33 pairs). The two MCPs also differ in file-write permissions on BP/Python tasks (MCP2 has no native write/edit/shell), so BP/Python differences between MCP1 and MCP2 are "not attributable to editor tools alone" (Sec. 4.1).
9. **Task set composition and exclusions (Sec. 3.1, 3.4, 8, App. F).** Tasks are bounded single-mechanism gameplay or editor behaviours selected for explicit checkability, proposed by the team (artists, designers, engineers) and filtered by the lead author; 50 start from the UE 5.8 Third Person template and 20 from a customised template; 47 further tasks were excluded for time and budget. Creative tasks needing visual judgement are excluded by design; screenshots "may be retained for diagnosis, but never to change the final grade".

## Corrections to the current literature-review.md entry (A6)
Entry: "70 tasks (C++, Blueprint, editor scripting) with deterministic build, asset and runtime checks and no LLM judge. Compared two editor-tool (MCP) configurations. C++ completion exceeds Blueprint by 30.0 and 42.9 percentage points on 10 paired tasks. 42.2% and 50.0% of asset-passing Blueprint submissions fail runtime assertions. In trajectories, "success revisions do not guarantee correct gameplay". They exclude creative tasks needing visual judgement. They note MCP-Unity and Epic's in-editor Unreal MCP as existing authoring tool sets. Informs: tool-interface design; ..."
- The numbers are right but need qualifiers: the 42.2% / 50.0% figures are 19/45 and 20/40 *on-time* (within 40 min) BP submissions on the ten paired gameplay tasks that pass asset checks; counting late submissions it is 24/70 (34.3%) and 28/70 (40.0%) of all final submissions. The 30.0 and 42.9 pp gaps are MCP1 and MCP2 respectively, over 7 models x 10 tasks with one attempt each.
- "Compared two editor-tool (MCP) configurations" understates the confound: MCP1 = three gateway entry points, MCP2 = 176 direct entry points, plus different file-write permissions and driver versions. The authors say the differences "compare these configurations; they do not identify the effect of an individual tool operation" (Sec. 2). The paper therefore gives no clean evidence about tool-granularity. Tool-surface *cost* (3.99x larger first request) is the one clearly measured effect.
- Missing conflict of interest: the authors' organisation (RamenVR) develops MCP2 (proprietary Aura MCP); the first author is presumably also the author of MCP-Unity (the cited "Wu & Barnett, 2025" is the same name). The review's Limits should say so.
- The entry says "They note MCP-Unity and Epic's in-editor Unreal MCP as existing authoring tool sets": true as a related-work remark (Sec. 2). Whether MCP1 ("Unreal MCP") is Epic's server is not stated explicitly; do not equate them.
- "Informs: tool-interface design" is weaker than it looks: the paper has no tool-design ablation. What it supports is (a) readback/inspection evidence matters more than write success, (b) the context cost of a large tool surface, and (c) that agents rarely run or look at the game unless pushed. Image capture is rare (about 6-9% of BP runs request one) and no screenshot ablation exists.
- Add: single attempt per cell, UE 5.8 on Windows, Claude Code as the only agent driver (non-Anthropic models via OpenRouter), harness announced as released and the repository exists but was not run by us.

## Design relevance
- **Structured runtime assertions are the paper's oracle, not images.** The task is graded on state at fixed timesteps (e.g. at 2.3 s: speed 122 vs 1405 cm/s, Power 14 vs 26 in App. A). This supports Gaia tools that can step the simulation by a fixed amount and read named state (eval + time advance), and an `assert-at-time` workflow, over screenshot-only verification. Evidence is about grading, not about what helps the agent while authoring.
- **Agents under-use runtime verification; successful edits are not a stop signal.** 24-30 of 175 BP runs read any state from the running game; asset readback is 149-165. Fifteen of 16 on-time failures after "clean" graph-write recovery failed runtime assertions. A Gaia tool result of "edit applied OK" should not terminate a task; the interface or prompt should require an observation of resulting behaviour (state after N ticks, or frames), and should say which behaviours to check (every required effect and the transitions between them, Sec. 6).
- **Playtest loops are a real failure mode.** The authors had to cap playtests at one per run after seeing loops. Gaia needs an iteration/time budget or a cost signal for "advance and look" calls, enforced in the tool rather than only in the prompt (here it was not enforced).
- **Tool surface cost.** A 176-tool surface made the first request 3.99x larger and the session cost 1.8x to 2.7x higher for five of six covered models (DeepSeek the exception), without a clear completion benefit on C++. Favour a small task-shaped tool set (or a catalog/gateway pattern) and concise descriptions, as the review already says; this paper is the measurement behind that, with the confounds above.
- **Deterministic replay design.** Reconstructing the saved submission in a fresh project and replaying at a fixed timestep with per-task tolerances is a ready pattern for Gaia's own regression checks (undo/snapshot plus fixed-step advance); the admission rule "reference passes, unchanged project fails" is a cheap validity test for any Gaia scenario test.

## Limits / credibility
- Preprint, v1, no stated venue; credibility-gate label: `context_or_prior_art_only`.
- 70 tasks selected for checkability, not sampled; single attempt per cell; 7 models; UE 5.8 on Windows; no repeated-attempt variance reported; no significance tests in the text I read.
- Industry-affiliated authors; one of the two MCP configurations is the authors' organisation's proprietary product. Authors state both configurations ran on the same tasks and verifiers and are reported separately.
- Task authors proposed behaviours and wrote verifiers; the task prompts name tolerances. Task validity relies on reference-pass / unchanged-fail checks, not on independent review.
- Trajectory analysis is observational (counts of tool-call categories), not causal; billing data are missing for direct-Anthropic runs and for BP/Python tasks.
- No visual feedback was graded or ablated, so nothing here supports or refutes screenshots as a feedback channel.
